PART 1 — KHATABOOK IN ONE PAGE

1. What it is

  • What: Bengaluru fintech building digital tools for India's small merchants: kiranas, wholesalers, small traders. India has about 6.3 crore MSMEs.
  • Started January 2019 (incorporated 2018). Co-founders: Ravish Naresh (CEO, earlier a Housing.com co-founder), Jaideep Poonia, Dhanesh Kumar, Ashish Sonone, Vaibhav Kalpe.
  • Origin: digitising the bahi khata, the red notebook where shopkeepers track udhaar (credit given to customers) and jama (payments received).

  • Mission line: "Simplify business, empower merchants" and "every business has the right to be digital".

PART 2 — MERCHANT PRODUCT ANALYTICS

1. Defining engagement for a kirana

  1. Core action, not app opens. Value happens when an entry is recorded and later collected.
  2. Weekly cadence. Shops log credit customers a few times a week; daily is noisy, monthly too forgiving.
  3. Depth: active days, entries per active day, customers managed.
  4. Outcomes: reminders sent, money collected via QR/payment links.
  5. Segment: business type, city tier, tenure, language.
  6. Validate: merchants above the threshold must retain better at 60/90 days.

2. North star

Weekly active merchants recording entries (threshold chosen by what best predicts 90-day retention). It captures value delivered, leads to revenue (lending eligibility and subscriptions need an engaged base), and is hard to inflate.

Reject: downloads/registered users (vanity), DAU of app opens (activity without value), total amount recorded (a few wholesalers dominate; one typo moves it). Pair with input metrics (activation, reminders, QR collections) and counter-metrics (uninstalls, complaints).

3. Churn

  • Define it for the cadence: e.g. no entry in 30 days. Separate dormancy and seasonal businesses (crackers, uniforms, harvest-linked shops).
  • Early churn vs late churn: never activated = onboarding problem; used for months then stopped = value or competition problem. Different owners, different fixes.
  • Cohort curves by signup month; segment by business type, tier, channel, language; rank by absolute churned merchants.
  • Behaviour before churn → early-warning signals (declining active days, never sent a reminder, no collections).
  • Why: exit surveys, calls, uninstall feedback. Act: interventions tested against a holdout.
  • False churn: reinstalls, new devices, late offline sync.

4. The offline-sync problem (Khatabook-specific, use it)

Merchants record entries without internet; the phone syncs later. So every entry has device time (created_at, when it happened, but the phone clock can be wrong) and server time (synced_at, when it arrived).

  • Report by event date, but treat recent days as provisional; rebuild a lookback window nightly sized from the sync-lag distribution.
  • Incremental pipelines must filter on synced_at, never created_at, or late entries are skipped forever.
  • A "drop this morning" is very often just devices that have not synced yet. Compare same weekday, same hour, by event vs sync time.

"In an offline-first app, today is always incomplete for a while, so I separate when an entry happened from when it reached us."

5. Adoption gap: Tier-1 vs Tier-2/3

Cheap to expensive: measurement (same denominator? events on old versions?) → rollout (feature flag, app version) → funnel (aware → tried → repeated) → context (vernacular language, literacy, low-end Android, storage, network) → business mix (compare within business type) → talk to merchants (field visits, support tickets) → pilot the fix.

6. Metric-drop checklist

  1. Is it real? Pipeline complete, freshness, sync lag, right baseline (same weekday/hour).
  2. What changed? Release, app version, Android update, OTP/SMS provider, Play Store, regional outage, festival/holiday/bandh.
  3. Where? Segment by state, language, version, device, channel; rank by contribution.
  4. Communicate: confirmed, ruled out, next update time.
  5. Prevent: alerts on freshness and sync lag; provisional labels; restatement policy.

7. Leading vs lagging

Lagging = outcome after the fact (monthly collected value, TPV, churn). Leading = moves earlier and predicts it (QR activation and first payment in week one, success rate). A leading indicator must be validated against the outcome and paired with it so it is not gamed.

PART 3 — SQL PATTERNS KHATABOOK ASKS

Think aloud: which table, which filter, what grain, what to compute. Interviewers care more about decomposition than syntax. Examples use Trino syntax.

1. Active one week, silent the next

WITH merchant_weeks AS (
  SELECT DISTINCT merchant_id, DATE_TRUNC('week', created_at) AS wk
  FROM ledger_entries
  WHERE is_deleted = FALSE
    AND created_at < DATE_TRUNC('week', CURRENT_DATE)      -- drop the week in progress
)
SELECT a.merchant_id, a.wk
FROM merchant_weeks a
WHERE a.wk < DATE_TRUNC('week', CURRENT_DATE) - INTERVAL '7' DAY
  AND NOT EXISTS (SELECT 1 FROM merchant_weeks b
                  WHERE b.merchant_id = a.merchant_id
                    AND b.wk = a.wk + INTERVAL '7' DAY);

The marks: distinct merchant-weeks first; anti-join; exclude the incomplete week or everyone looks churned.

2. Did A but never B

NOT EXISTS or LEFT JOIN … IS NULL. Never NOT IN on a nullable column: one NULL in the list returns zero rows, silently.

3. Month-over-month growth

SELECT city_tier, mon, value,
       (value - LAG(value) OVER w) * 100.0 / NULLIF(LAG(value) OVER w, 0) AS mom_pct
FROM monthly
WINDOW w AS (PARTITION BY city_tier ORDER BY mon);

Edges: complete months only; LAG takes the previous row, so missing months need a calendar spine; skewed values deserve a median alongside.

4. Outliers: more than 2 standard deviations

SELECT payment_id, merchant_id, amount
FROM (
  SELECT p.*,
         AVG(amount)    OVER (PARTITION BY merchant_id) AS mu,
         STDDEV(amount) OVER (PARTITION BY merchant_id) AS sd,
         COUNT(*)       OVER (PARTITION BY merchant_id) AS n
  FROM payments p WHERE status = 'success'
) t
WHERE n >= 30 AND amount > mu + 2 * sd;

Critique to volunteer: money is right-skewed (use log amounts, median/MAD or percentiles); the outlier inflates its own SD (use trailing history); output is candidates for review, not proof of fraud.

5. Weekly cohort retention

Cohort = signup week; week_n = DATE_DIFF('week', cohort_week, DATE_TRUNC('week', created_at)); retention = distinct active merchants ÷ full cohort size (including merchants who never recorded anything). Blank out cells a cohort has not reached yet. Say whether it is classic (exactly week N) or unbounded (week N or later) retention.

6. Also have ready

  • Top N per group: aggregate → rank in a CTE (ROW_NUMBER vs DENSE_RANK for ties) → filter outside.
  • Second highest without LIMIT: DENSE_RANK = 2, or MAX below MAX.
  • Threshold groups: GROUP BY … HAVING COUNT(*) >= 5.
  • Dedupe to latest version: ROW_NUMBER() OVER (PARTITION BY entry_id ORDER BY synced_at DESC) = 1.
  • Running totals and consecutive streaks (gaps and islands).

7. Query optimisation (explicitly in the JD)

  1. Measure: EXPLAIN / query plan, bytes scanned, which step dominates.
  2. Read less: filter the partition column directly (dt BETWEEN '20260801' AND '20260831', not a function wrapped around it); select only needed columns.
  3. Join less: pre-aggregate the big table before joining; check join keys have matching types; watch fan-out hidden by DISTINCT.
  4. Structure: incremental models, partitioning and clustering, materialised summary tables for dashboards hit all day.
  5. Re-measure and quote before/after.

PART 4 — PIPELINES: ELT, dbt, AIRFLOW

1. ELT and the modern stack

Extract/load with Airbyte (or CDC) into the warehouse raw layer → transform with dbt (staging → intermediate → marts) → orchestrate with Airflow → serve in Tableau / Power BI / Qlik. ELT won because cloud warehouse compute is cheap and keeping raw data lets you reprocess when logic changes. ETL still fits when PII must be masked before landing.

2. dbt in five lines

  • A model is a SELECT in a file; ref() and source() build the dependency graph and lineage.
  • Materialisations: view, table, incremental, ephemeral.
  • Tests: unique, not_null, accepted_values, relationships, plus custom SQL; freshness on sources.
  • Layers: stg_ (rename, cast, one per source) → int_ (joins, business logic) → fct_/dim_ (marts). BI reads only marts.
  • dbt does not extract, load or schedule.

3. Incremental model for an offline ledger

{{ config(materialized='incremental', unique_key='entry_id', incremental_strategy='merge') }}

SELECT entry_id, merchant_id, amount, entry_type,
       created_at, updated_at, synced_at, is_deleted
FROM {{ source('raw', 'ledger_entries') }}
{% if is_incremental() %}
WHERE synced_at > (SELECT MAX(synced_at) - INTERVAL '3' DAY FROM {{ this }})
{% endif %}

Watermark on synced_at (late offline entries and edits), merge on unique key (edits overwrite), lookback overlap (clock skew), soft deletes kept as a flag, periodic full refresh.

4. Airflow essentials

  • DAG of tasks; operators are task templates; dependencies set order; sensors wait for upstream data.
  • Retries with backoff, timeouts, SLAs, alerts.
  • Each run has a logical date / data interval; tasks use it, never now(), which makes backfills correct.
  • Airflow orchestrates; heavy compute happens in the warehouse.

5. Idempotency and backfills

"Re-running a load for the same day changes nothing." Overwrite the partition or delete-then-insert the date range; never blind append. Deterministic transforms. Backfill = the same task for a list of dates, throttled (max active runs), off-peak, validated by per-day counts and totals.

6. Data quality on a fact table

Unique grain key · not null keys · accepted values and ranges · referential integrity · freshness · volume anomalies · reconciliation to source of record. Grain/freshness failures block publishing: stale-but-correct beats fresh-but-wrong.

7. Reconciliation with Finance (named in the JD)

  1. Understand timing: transaction time vs settlement date (T+1), cut-offs, UTC vs IST.
  2. Full outer join on gateway transaction id / UTR.
  3. Classify breaks: missing either side, amount mismatch, status mismatch, duplicates.
  4. Model refunds, reversals, fees/MDR, chargebacks explicitly.
  5. Control totals within tolerance; daily automated breaks table with ageing and owners.

8. Automating a manual report

Requirements and exact definitions (including undocumented Excel adjustments) → dbt models on certified sources → Airflow after upstream loads → quality gate → parallel run 2–3 weeks and reconcile every difference → deliver where users work → document, hand over, measure hours saved.

9. Schema changes and contracts

Lineage to find blast radius → fix forward in staging → data contracts with producers → source tests (accepted values catches new enums; schema change detection catches renames) → slim CI on every pull request → owners and alerts.

PART 5 — EXPERIMENTS AND CAUSAL REASONING

1. A/B test for onboarding

  • Primary metric: activation = first ledger entry within 24h / 7 days (not "completed onboarding screens").
  • Randomise new installs at user/device level on first launch; never by city or week.
  • Sample size from baseline and MDE at 80% power; whole weeks; no peeking.
  • Guardrails: D30 retention, uninstalls, OTP completion, support contacts.
  • Analysis: SRM check first; pre-registered segments (language, tier, device).

2. "Reminded customers pay faster" — so do reminders work?

Selection bias: engaged merchants remind, and they pick customers likely to pay. Fix with a randomised holdout, randomising at merchant level to avoid spillover. Measure incrementality (recovered amount at 30–60 days), not just speed (a timing shift is not extra money). Guardrails: opt-outs, spam complaints, WhatsApp blocks. Fallbacks: difference in differences, propensity matching, regression discontinuity.

3. Statistics you will be asked

  • p-value, confidence interval, Type I/II error, power; t-test vs chi-square vs Mann–Whitney.
  • Mean vs median for skewed money data; z-scores and why they fail on skewed data.
  • Simpson's paradox: mix shift across tiers or business types.
  • Correlation vs causation; confounders; survivorship bias.

PART 6 — MERCHANT LENDING BASICS

1. The model

Khatabook sources and services; RBI-registered NBFC partners lend from their own books. Under RBI's digital lending guidelines the platform is a lending service provider: the loan goes from the lender to the borrower's account, the borrower gets a Key Fact Statement with the all-in APR, data is collected only with consent, and any default loss guarantee a platform gives a lender is capped (5% of the portfolio). You do not need legal detail; you need to know partners carry the risk and rely on our data.

2. Using ledger data for credit

  1. Trust hierarchy: verified cash flow (QR, payment links, UPI) > self-reported entries (can be gamed once merchants know they drive offers).
  2. Stability: tenure, consistent active weeks, regularity — not a burst before applying.
  3. Receivables health: outstanding udhaar vs collections, recovery rate, days to collect, customer concentration.
  4. External: bureau, partner policy.
  5. Validate: backtest on disbursed loans by vintage at equal months on book (30+ DPD separation).
  6. Launch: pilot with small tickets, exposure cap, stop rules. EDI repayment gives an early read.
  7. Traps: selection bias (repayment observed only for approved merchants), consent and regulation.

3. Risk metrics in one breath

Collection efficiency (collected ÷ due), EDI bounce rate, DPD buckets, FPD, roll rates between buckets, and vintage curves: group by disbursal month, plot delinquency by months on book, compare cohorts at the same age. A growing book always looks healthier in calendar terms because young loans have not had time to default.

"I would never show a blended default rate across cohorts of different ages; I would compare vintages at the same months on book."

3. Most likely business-head questions

  • Three stakeholders, three KPIs: understand the goal behind each → place on the metric tree → quantify → check conflicts and guardrails → make the trade-off visible with the shared manager → commit and revisit.
  • Prioritising a backlog: RICE or impact/effort, impact defined via the north star; weigh requests by merchants affected, not loudness; compliance is a must-do; data quality and tech debt scored as risk reduction; measure after shipping.
  • Explain to a non-technical head: headline first → one chart → how sure you are (correlation vs causation) → recommendation and decision needed → appendix.
  • First 90 days: learn and reconcile one metric end to end → own a report or fact table and automate it → deliver one analysis that changes a decision; document throughout.

4. Why Khatabook (template)

The users (crores of small merchants, many first-time business-app users) → the data problem (turning ledger and collections behaviour into credit decisions) → the role (Central Analytics owns pipelines and fact tables, not just dashboards) → lean, ownership-heavy team → one observation from actually using the app → what you bring.

Homework: install the app, add a customer, record an udhaar entry, send yourself a reminder, look at the QR and loan screens.
